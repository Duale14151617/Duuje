# Changelog

## Unreleased

### New: vehicle tracking upgrade and Puntland map
- **Puntland map.** Self-hosted PMTiles map (MapLibre) on the Vehicle tracking page and each vehicle's page; no third-party tile service. Served only to signed-in users with `vehicles.view`, with HTTP Range support and streamed responses. The map ships as three parts that the Dockerfile joins. Content-Security-Policy gains `worker-src 'self' blob:` (also in `deploy/nginx.conf.example`).
- **Zones.** Circle or polygon zones (station, post, restricted area) with entry/exit events, scoped to the caller's area.
- **Tracking.** Route trail with distance, silent-vehicle list, daily movement report with CSV export, tracker key rotation.
- **Position archive and purge.** Signed archives of old positions and a controlled purge (`archive_keygen`, `archive_positions`, `purge_positions`); positions stay append-only except for archived rows. See docs/POSITION_ARCHIVE.md.
- **Operations.** `reset_mfa` command with an optional `RESET_MFA_USERNAME` start-up hook; `tzdata` added for the report time zone.
- **Fixes.** `AuditEventViewSet` declares `throttle_scope` (the app failed to import under DRF 3.16 without it); a pending `medical` choices-only migration is now included.
- Somali text for the new screens is a draft and needs review.

### New: ID cards, official letters and scheduled reports
- **ID cards and official letters.** Printable officer ID cards (photo, rank, unit, validity, QR code) and letterhead letters with a QR code and a text fingerprint. Scanning the code opens a public check page (`/verify/<code>`) that says genuine, revoked, expired or not found, and shows only name, rank, unit and a partly hidden service number. New permissions `credentials.view` / `credentials.issue`. Needs the `segno` package (in requirements).
- **Scheduled reports by email.** Weekly/daily/monthly strength report emailed to commanders (counts only, verified-email recipients who can view the area). New permission `schedules.manage`, command `send_scheduled_reports`, and a token-protected trigger `POST /api/v1/schedules/run-due/` for an outside scheduler. See `docs/ID_CARDS_LETTERS_AND_SCHEDULES.md`.

### Rename: POLICEHQ_* environment variables
- Settings are now read through `apps/core/env.py`: `POLICEHQ_<NAME>` first, then the older `ARMYHQ_<NAME>` (and the oldest `ARMYHQ_DEMO_*`), so **existing deployments need no change**. When both are set the `POLICEHQ_*` one wins; a blank value counts as not set, so a blank new variable never hides the old one. The Django setting `ARMYHQ_PROFILE` is now `POLICEHQ_PROFILE`; the Dockerfile start command, `render.yaml`, `.env.example`, `docker-compose.local.yml` and the guides use the new names. The React component `ArmyStrength` is now `PoliceStrength`.
- Deliberately not renamed (renaming would change live data or behaviour): database and role names, `ARMY` branch and unit codes, the `*_army_structure` commands and modules (they describe the Army profile), Render resource names, session cookie names (renaming signs everyone out once), logger names and the `armyhq.E…` check ids.

### Promotion proposals
- On the promotion screen, people with `changes.propose` (headquarters administrator, super administrator) can select eligible people and **propose** their promotion. Each becomes a rank-change request in the normal change-request queue with the Police order reference, issuing officer and order date, decided by the super administrator (a super administrator's own proposal is applied at once, as everywhere in the queue). Eligibility is worked out again on the server, all rows are checked first and nothing is created if any is wrong, and someone with a request already waiting cannot be proposed twice.
- The next rank is the very next rank up in the same service, never skipped: if it is not approved yet the person shows as "No approved rank to promote to" and cannot be proposed.

### Leave requests and duty roster
- **Leave:** members ask for their own leave and commanders can ask for people in their unit. A commander with approval rights approves or rejects (a reason is required to reject); nobody decides their own request (only the super administrator, audited). Pending or approved leave can be cancelled before it starts. Overlapping leave for one person is refused. Leave types are data (annual, sick, compassionate, study, other; annual is capped at 30 days).
- **Roster:** a weekly duty roster per unit (day, night, standby, off). Someone on approved leave cannot be rostered for duty; the roster shows approved leave in the grid.
- New permissions `leave.own`, `leave.request`, `leave.view`, `leave.approve`, `roster.view`, `roster.manage`, granted to the unit commander (all), the regional commander (view) and members (own leave); the headquarters administrator receives them with the other unreserved permissions. Run `seed_reference_data` after deploying (the Docker start already does).
- **Leave in attendance:** days covered by approved leave count as "on leave" in the attendance roll, the attendance summary and the unit situation report, and the roll screen starts those soldiers as "on leave". It is read from the leave record rather than copied into the append-only attendance table, so cancelling leave needs no clean-up. Once the commander records a day, that record wins (a soldier called back early is recorded as present and counted once).
- Leave and roster do not change personnel status. Somali text is a working translation and needs review.

- **Leave notifications:** approvers (everyone holding `leave.approve` over the unit, except the person who asked) are notified when a request is pending; the requester, and the person the leave is for, are notified when it is approved or rejected, and the other side when it is cancelled. What a notification shows is checked again when it is read, so a change of scope reveals nothing. A failed notification never blocks the leave action. Adds `notifications.leave_request` (migration `workflows/0003`).

### Promotion eligibility
- Time in rank against a minimum for each rank (`promotion.view` for commanders and the headquarters administrator; only the super administrator sets the rules with `promotion.configure`). No minimums are seeded: they are the institution's policy, so every rank shows "no rule" until they are set. Time in rank counts from the last recorded rank change; where there is none it counts from when the rank was first entered, and the screen says so. Suspended or jailed people are shown as held back. This is advisory: it never changes a rank.

### Fitness for duty and medical records
- New append-only, encrypted fitness entries per person: status (fit, limited duty, unfit, under review), review date, a short non-diagnostic duty restriction, and medical details. Commanders with `fitness.view` see status, review date and restriction for their unit (with overdue reviews highlighted); the details need `medical.view`, held only by the new **medical officer** role (which also holds `medical.manage` to record and correct). The headquarters administrator can see fitness status but never the details. These permissions are gated like other personnel data (restricted units need `restricted.access`), every read and write is audited (never the text itself), and corrections form a single chain like disciplinary entries.

After "Create all accounts" the page offers **Print sign-in sheet (PDF)**: one row per new account with username, full name, role and unit, the temporary password, its expiry and a signature column, followed by the checklist. The passwords are in the sheet because the server shows them once and never stores them in clear; the sheet carries a warning to print once and destroy it when every row is signed. **First-login checklist (PDF)** is also available before creating accounts: sign in, choose a new password, install an authenticator app, "Show setup key", confirm the 6-digit code, add and verify an email (this is what makes self-service password recovery work), what to do if locked out, never share codes. English and Somali.
- **Shift handover** (`detention/0008`, page "Shift handover", `/api/v1/shift-handovers/`, `apps/detention/handover.py`). At the end of a shift an officer writes one note for the station: the **server copies who is in custody from the register** at that moment (register number, name, cell, hours held, review due, court soon, remand ended), the officer adds **pending** and **watch** (both required; "nothing" is a valid answer) and an optional note about the people held. **The next officer must acknowledge it**: the author cannot acknowledge their own note, an acknowledgement is final (one per note, enforced by a unique constraint), and **until the station's latest note is acknowledged nobody except its author can write the next one**. A note unacknowledged for `DETENTION_HANDOVER_ACK_HOURS` (default 12) is shown as overdue. Notes and acknowledgements are append-only (database triggers). Access reuses `detention.view` (read) and `detention.manage` (write, acknowledge), narrowed to the caller's stations; audit events `handover.create` / `handover.acknowledge` hold counts and ids, never names or the note text. "My work" shows how many notes are waiting for you. Each note can be printed as PDF. Tests: `detention/tests/test_handover.py`.
- **Personnel report** (`GET /api/v1/personnel-report/?from=&to=&unit=`, page "Personnel report", CSV and PDF like the custody report). Strength and movement for a period by region, unit and rank: on file, serving, each status, joined, left, promoted. **Counts only**: no names or service numbers, so it does not need the fresh-MFA step of the row-level `/personnel/export/`. Scope is the caller's `personnel.view` units; reading is audited (`personnel.read_report`). The definitions are printed on the page and in the PDF. Tests: `personnel/tests/test_report.py`.
- **Tax report by station** (`GET /api/v1/tax/oversight/?from=&to=&unit=`, page "Tax report by station", CSV and PDF). Per station and region for a period: receipts, amount collected per currency, voided, cash still with collectors, handovers, counted, handovers with a difference, active vehicles and vehicles lacking current cover. Amounts and counts only, no owners or plates; scope is `tax.view`; audited (`tax.read_oversight`). The existing daily collection report and overdue export are unchanged. Tests: `OversightReportTests` in `tax/tests/test_tax.py`.

### Offline mode (offline desk)
- **Offline desk** (`/offline-desk`, also linked from the sign-in screen): officers can book in a person and add custody-log entries (welfare, medical, visit, property, statement, note, review) with no internet, and send them when the connection returns.
- Entries are kept in an **encrypted vault on the device** (AES-GCM, key derived from a passphrase the officer chooses with PBKDF2-SHA256, 600,000 rounds, held only in memory). The passphrase cannot be recovered; a forgotten one means wiping the vault.
- Sending is **safe to repeat**: every entry carries a unique `client_ref`; the server creates nothing twice (migration `detention/0007_offline_client_refs`).
- Entries the server refuses (duplicate ID, record closed or moved, date rules) are **kept with the server's reason** and shown as "needs attention"; nothing is dropped silently. Officers can discard an entry on purpose.
- Offline entries are labelled "[entered offline]" in the custody log and audited with `offline: true`. Times come from the device clock (the desk warns about this).
- Not available offline by design: cell moves, releases, transfers, court dates, charges and incidents (they need current records and checks).
- Service worker v2 keeps the generic app shell (same file for every user, no personal data) so the desk opens with no signal. API responses and pages with data are still never cached.
- A banner shows entries waiting on the device, and signing out warns if any remain.

  expenditure**, **loss** and **damage**, next to receipt, issue, authorized **adjustment** and paired unit transfers.
- Controls: receipts, issues and returns need a voucher / delivery-note number and the same voucher cannot be booked twice for the same kind of
  movement on a line (database constraint); expenditure, loss, damage and adjustments need a reason; loss, damage and adjustments need a documented
  authorization; an adjustment also needs the explicit `logistics.reconcile` authority; the direction of every movement follows from its kind (database
  check); a negative balance is refused (service and database); every row is append-only, so an adjustment adds a new row (who, why, on whose authority)
  and never overwrites the original. Reconciliation corrections now carry their reconciliation as the authorization.
- The general stock route refuses ammunition (`use_ammunition_ledger`); ammunition is posted only through `/logistics/ammunition/`.
- Statement (`GET /logistics/ammunition/{line}/statement/?from&to`): balance at start, each kind of movement, closing balance, an integrity check (stored
  running balances against the sum of the movements, and against the current quantity), reconciliation counts with their variance and the number of
  discrepancies still open, and the movements.
- The unit situation report now uses these totals: balance at start, opening recorded, receipts, returns, adjustments up and down, issues, expenditure,
  loss and damage, transfers out, remaining. (The earlier `ammo_other_out` figure is replaced by these keys; drafts made before this upgrade must be re-saved.)
- Screen: Ammunition ledger (lines, statement for a period, record a movement, movement history). English and Somali.
- Posting needs `logistics.manage` + `logistics.restricted` over the unit (restricted custodians, weapons custodians); unit commanders can read their
  unit's statement but not post.
- Assumptions to confirm with the army: ammunition is tracked per type or calibre, each its own category; which movements need a voucher or a
  documented authorization; that returns are capped by cumulative issues on the same line; who may adjust (reconcile authority only); whether
  expenditure needs its own document; the opening balance date. Rounds are whole numbers.
- Tests: `logistics/tests/test_ammunition.py`. Not run at time of writing (no Django here).

## Unreleased: Weapon register (requirements step 4)
- New `weapons` app (migration weapons 0001). Weapons are tracked **individually by unique serial number** on the existing restricted asset ledger
  (category `weapons`, restricted, seeded as a draft until the restricted-approval authority approves it). The serial is unique across the whole
  register, in any unit and any weapons category. **No quantity totals are stored:** counts per type, unit, status and condition are derived from
  the register. Quantity-based stock (for example ammunition) stays in the inventory ledger.
- Personal custody: `WeaponCustody` records which soldier holds which weapon, from issue to return: issue and return dates, issuing and receiving

- Rules: one holder at a time (database constraint); the person must be serving and in the unit holding the weapon; unserviceable weapons are not
  issued; a stale version is refused. While in custody the weapon shows as issued to the soldier's unit and the ordinary asset actions (transfer,
  retire ...) are refused, except reporting it lost or missing, which closes the custody. A weapon issued to a unit and then to a soldier returns
  to the unit state it had. The general asset route can no longer create weapons (they need their type and custody record).
